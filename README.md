# Craft BD

A digital marketplace connecting Bangladeshi artisans with customers who care
about provenance, craft, and cultural memory.

**Current build: Chunk 3 — artisan showcase and profiles.** Chunks 1
(foundation), 2 (catalogue), and 4 (provenance verification) are complete.
Commerce, reviews UI, admin tools, and artisan dashboards arrive in later
chunks.

## Stack

- Next.js 16 App Router (TypeScript, React 19)
- Tailwind CSS v4 + shadcn/ui conventions + Lucide icons
- Supabase Postgres, Auth, and Row Level Security
- `@supabase/ssr` with Next.js Proxy session refresh

## What is in Chunk 4

- `/verify`, a public lookup page that accepts a certificate code such as
  `CBD-JAM-2026-0001` and needs no account.
- `/verify/[code]`, a printable certificate record showing the piece, product
  ID, artisan, craft tradition, origin, materials, production stages, issue
  date, status, and payload hash.
- A field-by-field integrity check against the live catalogue: certificate
  code, product record and title, artisan record and name, craft, origin,
  materials, and issue date are compared with the stored payload.
- Clear wording that verification confirms the certificate record, not the
  physical item itself.
- Distinct authentic, mismatch, and revoked states, including revocation reason
  and date where recorded.
- Server-rendered QR codes (inline SVG) that open the same verification URL on a
  phone, plus a print action with site chrome hidden.
- `/scan`, an in-app camera scanner using the native `BarcodeDetector` where
  available and `jsQR` as a fallback. It accepts only same-origin verification
  URLs or a valid raw certificate code. Camera access requires HTTPS or
  `localhost`; manual code entry remains available.
- `/verify/[code]/label`, a printable product QR label with SVG and PNG
  downloads generated by `/api/qr/[code]` from the request origin, so labels
  point at the live domain rather than a hard-coded URL.
- "Verify this product" and "Product QR label" links from the product
  certificate card, the verification page, the home page promise section, and
  the site footer.
- Verification detail pages and QR label pages are `noindex`; the lookup and
  scan pages are indexable.

## What is in Chunk 3 — artisan showcase

- `/artisans`, a public directory of every approved studio with a cover image,
  portrait, craft specialisation, district, and published piece count.
- Deterministic, URL-driven filters for search (`q`), craft tradition (`craft`),
  region (`region`), and sort (`featured`, `name`, `experience`). Matching runs
  in memory over the approved set, so results are stable and do not need a
  database migration.
- `/artisans/[slug]`, a studio profile with a cover header, portrait, craft and
  place facts, languages, years at the craft, full biography, aggregate review
  rating, and a grid of that studio's published pieces.
- Related studios chosen deterministically by shared craft tradition and region.
- Product detail pages and the product-page maker card link back to the studio
  profile; the home page adds a feature-makers section.
- Artisan reads are cached with `'use cache'`, `cacheLife('hours')`, and the
  `artisans`/`catalogue` tags, using the same cookie-free public Supabase client
  as the catalogue.
- Directory, profile loading states, a studio not-found page, and a directory
  error boundary.

## What is in Chunk 3 — accounts and authentication

- Email/password sign-up, sign-in, and sign-out through Supabase Auth. Craft BD
  never stores or handles credentials itself.
- `/account`, a protected dashboard that shows the signed-in profile, role, and
  membership date.
- Profile editing for full name and phone number, with the email shown
  read-only until a dedicated email-change flow exists.
- Password change from the account page, plus a single-use
  forgot/reset-password flow delivered by email.
- `/auth/callback` exchanges Supabase email links for a cookie session and
  returns the visitor to a validated same-origin path.
- An auth-aware header account menu, optimistic `/account` protection in the
  Next.js Proxy, and authoritative JWT checks in every protected page and
  Server Action.
- Server-side Zod validation, accessible field errors, pending states, and
  rate-limit messaging for every auth form.

> Email confirmation follows the Supabase project setting. When it is enabled,
> new accounts see a "check your inbox" message and can sign in after confirming;
> seeded demo accounts are already confirmed.

## Prerequisites

- Node.js 20.9+ (Node 22 is used in development)
- A Supabase project (hosted) **or** Docker Desktop for local Supabase CLI use
- Supabase CLI (installed as a dev dependency; `npx supabase` also works)

## 1. Install and configure

```bash
npm install
cp .env.example .env.local   # Windows: copy .env.example .env.local
```

Fill `.env.local` from **Supabase Dashboard → Project Settings → API**:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://your-project-ref.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=your-publishable-key
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key
```

Older Supabase projects can use `NEXT_PUBLIC_SUPABASE_ANON_KEY` instead of
`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; the app accepts either.

`SUPABASE_SERVICE_ROLE_KEY` is server-only. Never expose it in client code.

## 2. Apply the schema and seed

### Hosted Supabase (recommended when Docker is unavailable)

```bash
npx supabase login
npx supabase link --project-ref <your-project-ref>
npm run db:push
```

`db:push` runs `supabase db push --remote --include-seed`, applying both
migrations and `supabase/seed.sql`.

### Local Supabase (requires Docker)

```bash
npm run db:start
npm run db:reset
```

`db:reset` replays migrations and `seed.sql`. Local API: `http://127.0.0.1:54321`.

### Verify without a database

```bash
npm run db:verify
```

This starts a throwaway in-process Postgres (PGlite) with a stubbed Supabase
auth schema, runs both migrations and the seed, and asserts row counts,
six-stage journeys, primary images, certificate hashes, RLS enablement, and
other invariants. It is a test harness only; the app always uses Supabase.

## 3. Run the app

```bash
npm run dev
```

Open `http://localhost:3000`. The catalogue is server-rendered and reads from
Supabase, so `.env.local` must point at a project with the migrations and seed
applied. Public pages remain readable through the anon/publishable key; no
service-role key is needed for browsing.

Key routes:

| Route | Purpose |
| --- | --- |
| `/` | Home, live catalogue stats, featured pieces, featured makers, craft traditions |
| `/products` | Catalogue grid with facets, sorting, and pagination |
| `/products/[slug]` | Product detail, craft story, journey, artisan, certificate |
| `/artisans` | Public artisan directory with search, craft, region, and sort |
| `/artisans/[slug]` | Studio profile, biography, rating, and published pieces |
| `/verify` | Public product and certificate code lookup |
| `/scan` | In-app camera scanner for product QR labels |
| `/verify/[code]` | Printable provenance record and integrity check |
| `/verify/[code]/label` | Printable product QR label with SVG/PNG downloads |
| `/api/qr/[code]` | QR SVG or PNG (`?format=png`, `?download=1`) |
| `/login` | Email/password sign-in |
| `/signup` | Create an account |
| `/forgot-password` | Request a password reset link |
| `/reset-password` | Choose a new password from a valid reset session |
| `/account` | Protected profile, password, and session management |
| `/auth/callback` | Handle Supabase email confirmation and recovery links |

## Data model

| Area | Tables |
| --- | --- |
| Accounts | `profiles` |
| Craft taxonomy | `categories` |
| Artisans | `artisans` |
| Catalogue | `products`, `product_images` |
| Cultural storytelling | `craft_stories`, `craft_journeys` |
| Provenance | `certificates` |
| Commerce | `addresses`, `orders`, `order_items` |
| Custom orders | `custom_orders`, `custom_order_events` |
| Feedback | `reviews` |
| Cart & wishlist | `carts`, `cart_items`, `wishlists` |
| Admin audit | `admin_actions` |

Key rules enforced by the database:

- Money is `numeric(12,2)` in BDT; order and line totals are generated columns.
- A published product must have a publish date; stock cannot go negative.
- Every product can have one craft story, six ordered journey stages, one
  active certificate, and one primary image.
- Customers can only review products from a delivered order item.
- Artisans can manage their own products/images/stories/journeys, but only
  admins can change artisan approval status, featuring, or role.
- Admin authorization uses the signed JWT `app_metadata.role`, not a mutable
  profile column.
- Certificate payloads are hashed with SHA-256; `npm run db:verify` recomputes
  every hash.

## Scope note

AI-driven recommendations (FR-13) are intentionally excluded. All discovery,
filtering, and gift suggestions are deterministic database queries over
category, region, materials, price, occasion, and stock.
